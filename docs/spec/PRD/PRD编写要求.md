# PRD 编写要求

## 文档目的

本文件定义了 Openthedoor 项目 PRD（产品需求文档）的编写规范、结构要求和质量标准。任何 Agent 或人员均可根据本文件 + `需求访谈记录.md` 撰写出一份完整的 PRD。

## 输入材料

- **必读**：`需求访谈记录.md` — 包含 148 条已确认的产品决策，是 PRD 的唯一事实来源
- **参考**：`全流程图.md` — 已绘制的全流程图，可直接引用或整理后纳入 PRD

## 输出要求

- 输出文件：`PRD.md`
- 格式：Markdown
- 语言：中文
- 要求：一份完整的单文件 PRD，不拆分为多个文件

---

## 写作原则

### 原则 1：事实来源唯一

PRD 中的所有产品决策必须来源于 `需求访谈记录.md`。不得自行发明需求、推测用户意图或补充未经确认的功能。如果某个细节在访谈记录中缺失，应在 PRD 中标注为"待确认"而不是自行填充。

### 原则 2：兼顾人类阅读和 AI Agent 阅读

本 PRD 不仅给人看，也会交给 Claude Code 等 AI Agent 作为开发参考。因此需要同时满足两类读者的需求：

| 要求                                                 | 原因                                |
| ---------------------------------------------------- | ----------------------------------- |
| 术语必须在文档开头统一定义，后续全文使用一致的命名   | AI 不会像人一样"猜"同义词           |
| 业务规则用 `if/then` 格式表达，并编号                | AI 处理条件逻辑比处理散文叙述更准确 |
| 字段定义用表格列出（名称、类型、约束、必填性、示例） | AI 可直接对照生成数据模型代码       |
| 状态转换用明确的 `当X → 则Y` 格式，不要用模糊描述    | AI 按字面意思执行，歧义=bug         |
| 每个功能模块自包含，包含该模块需要的所有信息         | AI 可能只读某一个模块来完成开发任务 |
| 验收标准用可测试的具体条件                           | AI 可据此生成测试用例               |
| 枚举值必须穷举列出                                   | AI 不会自行推断"还有哪些值"         |

### 原则 3：结构化优于叙事化

- 优先使用表格、列表、枚举，而非长段落描述
- 复杂逻辑用 `if/then` 或状态转换表，而非自然语言
- 流程用步骤编号，而非连续叙述
- 每条业务规则独立编号（如 R1、R2...），方便后续代码中引用

### 原则 4：精确优于简洁

- 不使用"等"、"之类的"、"类似"等模糊表述
- 字段约束必须写明具体数值（如"25-64 字符"而非"简短"）
- 状态枚举必须列出全部可能值
- 如果有特例或边界情况，必须显式写出

## PRD 结构

### 第一部分：全局上下文

#### 0. 文档信息

- 版本号（初始版本 1.0）
- 日期
- 状态（草稿/评审中/已定稿）
- 基于需求访谈记录版本（148 条）

#### 1. 产品概述

编写要求：

- 一句话定位
- 要解决的核心问题
- 目标用户（两类角色）
- 核心价值主张
- MVP 边界（做什么 + 明确不做什么）
- 平台行业范围

数据来源：访谈记录 #1-#3, #122, #123

#### 2. 术语表与全局约定

编写要求：

- 用表格列出所有专有名词及其精确定义
- 必须包含的术语至少有：Openclaw、卡片（求职卡片/招聘卡片）、私密信箱、关系状态、claim link、API Key、heartbeat、用户联络账号
- 全局业务规则编号列表（R1, R2, R3...），这些规则适用于所有功能模块
- 行为准则（6 条，来自 #140）
- 不可披露信息清单（来自 #121）

数据来源：贯穿整个访谈记录，术语散布在各条目中；行为准则 #140；不可披露清单 #121

### 第二部分：数据与状态

#### 3. 数据模型

编写要求：

- 列出所有核心实体：用户、Openclaw、招聘卡片、求职卡片、私密信箱、消息
- 每个实体用表格定义字段：字段名 | 类型 | 约束 | 必填 | 说明 | 示例值
- 明确实体之间的关系（一对一、一对多等）
- 明确数据存储边界（哪些在平台服务端，哪些在用户本地）
- 注意：访谈记录中已确认两侧卡片的所有字段，必须完整列出，不可遗漏

招聘卡片字段来源：#10-#18, #21-#34, #36-#37
求职卡片字段来源：#35, #38-#60, #148（专业技能重命名）
数据存储边界来源：访谈记录中"数据存储边界补充"部分
Openclaw 基础资料来源：#125-#127
用户信息来源：身份接入相关条目

#### 4. 状态机定义

编写要求：

- 三层状态机分别独立定义
- 每个状态机用表格列出：状态值 | 含义 | 进入条件 | 可转换到的下一状态
- 联动规则用 `当X → 则Y` 格式明确写出
- 必须覆盖所有已确认的状态值，不可遗漏

三层状态机：

1. 卡片发布生命周期：`启用中`、`暂停中`、`已关闭`（#100-#103, #146）
2. 卡片关系状态：`未读`、`已读`、`已发起对话`、`已拒绝`、`已交换`、`已超时`（#71, #99, #143）
3. 私密对话状态：`进行中`、`已拒绝`、`待用户回复`、`已交换`、`已超时`（#70-#75, #137）

联动规则来源：#72-#74, #143
卡片生命周期切换语义来源：#102-#103, #146

### 第四部分：功能规格

#### 6. 功能模块

每个模块必须包含以下子结构（严格遵守，不可省略任何一项）：

```
## 6.X 模块名称

### 功能描述
做什么、为什么做

### 涉及角色
谁触发、谁受影响

### 业务规则
编号规则，用 if/then 格式：
- BR-6.X-01: 当 [条件] 时，[动作/结果]
- BR-6.X-02: ...

### 涉及的 CLI 操作
列出本模块用到的 CLI 操作及其在本模块中的作用

### 涉及的数据模型
引用第 3 章中的相关实体和字段

### 涉及的状态变更
引用第 4 章中的相关状态转换

### 边界条件与异常处理
明确写出异常场景及处理方式

### 验收标准
可测试的具体条件，用 checkbox 格式：
- [ ] 条件描述
```

需要编写的功能模块清单：

**6.1 入驻与认领**

- Openclaw 注册（含必填参数、返回值）
- claim link 生成与重新生成
- 用户认领流程（Gmail magic link）
- 认领成功/失败处理
- 数据来源：#112, #125-#129, 身份接入相关条目

**6.2 信息采集**

- 固定标准说明文案（求职者版 + 招聘者版，直接引用 #139 的完整文案）
- 本地档案生成规则
- 数据来源：#105-#106, #113, #117-#118, #139, 求职者/招聘者信息采集相关条目

**6.3 卡片发布与管理**

- 卡片发布（两类卡片的字段清单、必填性、长度约束）

- 数据来源：#10-#60, #92-#94, #100-#103, #130, #138, #146

**6.4 发现与筛选**

- 列表浏览（两类列表的展示字段、标题模板、排序逻辑）

**6.5 私密信箱与对话**

- 创建机制（首次发送消息时自动创建）

- 拒绝规则（必须附带理由）
- 邀约规则（接收方可接受或继续提问）
- 对话限制（软上限 20 轮 / 硬上限 40 轮 / 时间 7 天）
- 卡片变更感知（系统消息注入）
- 并行处理（同一卡片可有多个信箱，agent 可并行处理）
- 数据来源：#62-#75, #92-#96, #104, #116, #132-#134, #138, #147

- 详细报告隐私边界（不含社媒/谈判策略，可含最低薪资/预算底线）
- 用户同意/不同意/未回复的处理
- 社媒账号提交与交换
- 拒绝分支的隐私保护（只反馈大致拒绝原因）

**6.7 通知与 Heartbeat**

**6.8 数据看板**

- 数据来源：#107-#111, #136

**6.9 网站页面**

## 质量检查清单

PRD 编写完成后，必须逐项检查：

- [ ] 所有术语是否在术语表中定义，且全文使用一致
- [ ] 所有字段是否有明确的类型、约束、必填性定义
- [ ] 所有状态枚举是否穷举列出
- [ ] 所有状态转换是否有明确的触发条件
- [ ] 所有联动规则是否完整覆盖
- [ ] 所有业务规则是否编号且使用 if/then 格式
- [ ] 所有功能模块是否包含完整的子结构（描述/角色/规则/CLI/数据/状态/异常/验收）
- [ ] 所有 CLI 操作是否有输入参数和输出定义
- [ ] 所有"前后修正"的条目是否以最终版本为准
- [ ] Out of Scope 是否完整列出
- [ ] 验收标准是否可测试（不是模糊的"正常工作"）
- [ ] 没有使用"等"、"之类的"、"类似"等模糊表述
- [ ] 没有自行发明访谈记录中不存在的需求
