## 1. 与访谈记录的一致性问题

以下问题是 PRD 与需求访谈记录之间存在的偏差或遗漏。

### 1.1 #67 "无需反馈给用户"行为规则缺失

**来源：** 访谈 #67

**访谈原文：**
> 当对方未给出明确态度时，agent 应把此状态标记为"无需反馈给用户"，避免打扰用户。

**PRD 现状：** 行为准则（2.3 节）和 Skill 规格（8 节）均未捕捉到这条行为指导。

**影响：** 如果 Openclaw 在对方无明确态度时频繁打扰用户询问，会违背"辅助用户更快筛选，而不是让用户频繁介入"的核心原则。

**建议：** 在 Skill 规格（8 节）或行为准则（2.3 节）中补入一条规则：当对方 Openclaw 尚未给出明确态度时，不应主动向用户反馈该对象的进展，避免无意义打扰。

---

### 1.2 注册联络账号与交换联络账号的概念区分未显式说明

**来源：** 访谈 #135

**访谈原文：**
> 注册时绑定的联络账号是为了保证每个 Openclaw 背后有真人。交换时提交的联络账号是用户实际想在后续真人沟通中使用的，两者可以不同。这意味着注册绑定的账号和交换时的账号是两个独立概念：前者是身份验证，后者是沟通渠道。

**PRD 现状：** BR-6.6-10 允许了"可以与注册时绑定的不同"，但未在术语表或全局规则中显式说明这两个概念的定位区别。

**影响：** 开发团队可能对"注册时的联络账号到底干什么用"产生理解偏差。

**建议：** 在术语表（2.1 节）或全局规则（2.2 节）中新增一条说明，明确区分两者的定位：
- 注册时绑定的联络账号 = 身份验证目的（证明背后有真人）
- 交换时提交的联络账号 = 实际沟通渠道（用户自选）

### 1.3 list-cards 未显式约束"只能查看对侧卡片"

**来源：** 访谈全流程一致强调"求职者的 Openclaw 浏览招聘卡片 / 招聘方的 Openclaw 浏览求职卡片"

**PRD 现状：** 7.8 节 `list-cards` 的 `card_type` 参数描述为"要查看的卡片类型"，没有显式约束 Openclaw 只能查看与自己角色相反的卡片类型。

**影响：** 按当前定义，招聘方的 Openclaw 理论上可以调用 `list-cards(card_type=recruitment)` 来浏览其他招聘方的卡片，这不符合产品意图。

**建议：** 在 7.8 节的业务规则或说明中明确：系统自动限制 Openclaw 只能查看与自己已发布卡片类型相反的卡片列表。或在全局规则中补充此约束。

---

### 1.4 #108 候选指标未记录为后续扩展

**来源：** 访谈 #108

**访谈原文：**
> 候选指标包括：谈了多少个人、拒绝了多少个人、已交换多少、回复率、别人主动找你沟通的概率、被人拒绝的数量、主要的拒绝理由、主要拒绝别人的理由。

**PRD 现状：** 最终 Top 4 指标正确收敛（#109），但其余候选指标（回复率、主动找你沟通概率、拒绝理由分布等）未在 Out of Scope 或后续迭代计划中记录。

**影响：** 产品迭代时缺少参考，需要重新翻阅访谈记录。

**建议：** 在 6.8 节或 11 节（Out of Scope）中补充"后续可扩展的指标"列表。

### 1.5 close-card 对存量私密信箱的具体处理方式缺失

**来源：** 访谈 #102（"已关闭=停止新增、停止存量继续，仅保留历史只读"）

**PRD 现状：**
- 4.1 节说"停止新增、停止存量继续，仅保留历史只读"
- 7.7 节副作用说"所有进行中的私密信箱停止"
- **但未定义"停止"后这些信箱的状态变为什么**

**影响：** 这是一个会直接导致开发歧义的缺失。具体问题：
- "进行中"的私密信箱关闭后，状态变为"已超时"？"已拒绝"？还是需要新增一个状态
 "进行中"的私密信箱关闭后 状态变为 已拒绝
- "待用户回复"的私密信箱关闭后如何处理？用户还能继续回复吗？
 统一系统恢复，当前职位或者当前求职者已停止招聘或者求职，用户不能回复了。
- 对应的关系状态联动规则是什么？


**建议：** 在 4.3 节或 7.7 节中明确定义 close-card 触发时各状态私密信箱的处理方式及状态转换规则。

## 2. PRD 自身完善度问题

以下问题不是与访谈记录的偏差，而是 PRD 作为产品需求文档本身需要补充的内容。

### 2.1 非功能性需求全部待定

**位置：** 第 10 节

**现状：** 6 个非功能性指标全部标注为"待确认"，该节实质为空。

**影响：** 🔴 **高**。非功能性需求直接影响架构设计和技术选型。开发团队无法据此做出基础设施决策。

**建议至少定义以下基础值：**

| 项目 | 建议初始值 | 理由 |
|------|----------|------|
| heartbeat 建议频率 | 5 分钟 | 平衡实时性与 API 调用量 |
| 私密信箱单条消息体大小限制 | 10,000 字符 | 防止无限长消息导致存储和传输问题 |
| API 响应时间基线 | P95 < 2s | 基础可用性保障 |
| 数据保留策略 | 已关闭/已超时数据保留 180 天 | 合规与存储成本平衡 |
| claim link 有效期 | 7 天 | 防止无限期有效的安全风险 |
| magic link 有效期 | 15 分钟 | 业界通用标准 |

### 2.2 claim link / magic link 有效期未定义

**位置：** 6.1 节、6.9 节

**现状：** BR-6.1-03 提到"claim link 丢失或过期"，边界条件表也写了"claim link 过期"的处理方式，但**从未定义"过期"的具体时间**。magic link 同样没有过期时间定义。

**影响：** 🔴 **高**。没有有效期定义，开发无法实现过期判断逻辑。

**建议：** 在 6.1 节业务规则中新增：
- claim link 有效期定义（建议 7 天）
- magic link 有效期定义（建议 15 分钟）
- 过期后的用户提示文案要求

### 2.3 通知实体数据模型缺失

**位置：** 第 3 节（数据模型）、7.15 节（check-notifications）

**现状：** `check-notifications` 返回"未处理通知列表"，但 PRD 没有定义通知实体的数据结构。6.7 节也标注"无独立数据模型，通知内容复用已有实体"，但没有说明复用的具体结构。

**影响：** 🟠 **中高**。前后端开发需要知道通知列表中每一条通知长什么样。

**建议：** 在 3 节中新增通知实体定义，或在 7.15 节的输出中明确通知的返回结构，至少包含：

| 字段 | 说明  |
|------|------|
| notification_type | 通知类型（新消息 / 收到邀约 / 对方已同意交换 / 系统消息） |
| mailbox_id | 关联的私密信箱 ID |
| from_card_id | 来源卡片 ID |
| created_at | 通知产生时间 |
| summary | 通知摘要 |

### 2.4 邀约双向确认的具体机制未充分定义

**位置：** 6.6 节、7.13-7.14 节

**现状：** PRD 定义了 `send-invitation` 和 `accept-invitation` 两个操作，以及"双方都接受邀约后状态变为待用户回复"。但以下问题未回答：

1. A 先 `send-invitation`，B 收到后也 `send-invitation`（而非 `accept-invitation`），是否算双方都接受？
2. A 发了邀约后 B 没接受也没拒绝，继续提问了 3 轮后才 `accept-invitation`，A 的邀约还有效吗？
3. A 发了邀约后 B 继续提问，A 是否可以撤回邀约？
4. 双方是否可以同时独立发送 `send-invitation`（不是一方发、另一方接受，而是同时发）？

**影响：** 🟠 **中高**。邀约是核心流程的关键环节，机制不清晰会导致实现分歧。

**建议：** 在 6.6 节中补充邀约的完整交互流程图和边界条件说明。明确：
- 邀约的生命周期（是否会过期、是否可撤回）
- 双方同时发送邀约的处理方式
- 邀约发出后对方继续提问时邀约是否保持有效

### 2.5 API 限流 / 防滥用机制缺失

**位置：** 无（整个 PRD 未涉及）

**现状：** 没有任何 API 调用频率限制定义。

**影响：** 🟠 **中**。一个 Openclaw 可以短时间内调用 `list-cards` 上千次、或批量注册大量 Openclaw，平台缺乏防护。

**建议：** 在第 10 节（非功能性需求）或新增一个"安全与防滥用"章节中，定义基本的 rate limiting 原则：
- 每个 API Key 的调用频率上限（如每分钟 60 次）
- `register` 接口的防刷机制
- 超限后的响应策略（返回 429 Too Many Requests）

---

### 2.6 CLI 操作的幂等性未定义

**位置：** 第 7 节（CLI/API 接口定义）

**现状：** 没有定义任何 CLI 操作的幂等性要求。

**影响：** 🟠 **中**。网络超时重试是 Agent 场景的常见情况。例如：
- `submit-social-media` 调用成功但 Openclaw 未收到响应，重试会怎样？会提交两次吗？
- `reject` 被重复调用怎么办？
- `send-message` 重试是否产生重复消息？

**建议：** 在全局规则（2.2 节）或第 7 节开头新增幂等性说明，至少标注哪些操作是幂等的、哪些不是，以及推荐的重试策略。

### 2.9 风险评估缺失

**位置：** 无

**现状：** PRD 没有识别任何产品风险或技术风险。

**影响：** 🟡 **中低**。缺乏预见性，可能在开发/上线后遇到未预期的问题。

**建议：** 新增一个"风险与应对"章节，至少识别以下风险：

| 风险 | 影响 | 应对思路 |
|------|------|---------|
| Openclaw 在对谈中违反行为准则 | 用户隐私泄露或体验受损 | Skill 中强化规则约束；后续考虑服务端内容审核 |
| 冷启动阶段供需严重失衡 | 一侧卡片过多另一侧过少 | 成功指标中已包含"供需平衡"指标；考虑种子用户策略 |
| Openclaw 质量参差不齐 | 对话质量差导致用户信任下降 | 用户同意率作为北极星指标可间接监控 |
| 7 天超时上限过短或过长 | 过短则深度对话被截断；过长则资源浪费 | 上线后基于数据调整 |
