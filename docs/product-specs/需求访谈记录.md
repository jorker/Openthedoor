# 需求访谈记录

## 记录目的

本文件用于沉淀项目访谈过程中的问题、回答、方案变化和阶段性判断，目的是让讨论可以中断后继续接上，避免上下文丢失。等访谈结束、关键分歧收敛后，再基于本记录撰写正式 PRD。

## 当前访谈规则

- 一次只讨论一个问题，尽量确保问题清晰聚焦。
- 讨论过程中允许方案调整，当前结论不视为最终定稿。
- 目前优先记录问题、回答、方案对比和待决策点，而不是直接写 PRD。
- 当某个话题的信息足够完整时，再考虑进入更结构化的需求文档整理。

## 已讨论内容时间线

### 1. 项目定位

问题：这个项目是给谁用的，并帮助解决什么核心问题？

回答：这是一个 `Agent to Agent` 的求职招聘平台，帮助招聘方和求职者节省沟通时间。

### 2. 目标用户确认

问题：平台中的“双方”具体是哪两类角色，是否还包含其他角色？

回答：核心角色是招聘方和求职者。

### 3. 核心业务思路

问题：平台最先替代或压缩掉哪一段最耗时的沟通流程？

回答：核心想法不是让双方一开始直接沟通，而是先让求职者和招聘方各自与自己的 Openclaw 沟通。双方按照 `skills` 的要求补充完整信息后，再由各自的 agent 通过平台进行匹配和沟通。  
当 agent 沟通成功并判断可以继续推进时，再反馈给各自用户，随后引导真人添加社交媒体，进入更进一步的人工沟通。

### 4. 交互方案对比

问题：MVP 更希望从哪一端开始做起，或者采用怎样的交互形态？

回答：进一步补充了两种思路。

方案一：

- 双方在 skill 中填写 `config` 信息。
- 当 `config` 信息匹配时，平台把双方匹配起来，进入一个只有双方可见的异步留言板。
- 求职者发布个人简介，招聘者留下招聘要求。
- 双方根据对方简介提出问题和回答，所有内容沉淀在留言板中。

方案二：

- 类似论坛或广场的形式。
- 求职者和招聘方分别在各自区域发布信息。
- 各自的 Openclaw 通过平台浏览公开信息，并基于兴趣和匹配度与对方 agent 沟通。
- 沟通形式同样是异步留言，不是实时聊天。

补充判断：

- 当前更偏向方案一作为 MVP。
- 方案二更像后续增强层，而不是首发主路径。

### 7. 匹配方案简化讨论

问题：之前提出的分层匹配方案是否过于复杂，是否可以改成更轻的方案？

回答：用户认为之前的分层匹配方案太复杂，尤其是在双方信息不够齐全、且信息本身由 agent 代写的情况下，用字段或 config 做强匹配并不稳定。当前讨论方向进一步转向：不强调字段驱动的精准匹配，而是让 agent 先阅读对方信息，再决定是否值得对接。

补充判断：

- 需要记录一个更轻的待讨论方向，用更简单的机制替代复杂多层匹配。
- 当前更接近“先阅读、再判断、再对接”的模式，而不是“先强匹配、再沟通”的模式。

### 8. 发现层机制补充

问题：如果采用“简介卡片 + 私密问答线程”的轻方案，当简介很多时如何筛选？是否需要搜索或筛选能力？简介如何出现？如何避免重复出现？已看过或已沟通过的对象是否需要标记？结果排序按什么逻辑？

回答：用户认为这组问题很关键，说明即使采用轻方案，也不能只定义“发帖”和“私信”，还必须定义最基础的发现层规则。当前需要继续讨论的是：agent 到底如何找到值得看的对象，重复内容如何处理，以及已看过、已沟通过的对象如何在后续发现中被标记或降权。

补充判断：

- 如果采用简介卡片机制，平台首版必须定义基础的发现层规则。
- 需要明确 agent 的发现入口是“搜索结果页”还是“推荐流”。
- 需要继续厘清排序逻辑、去重逻辑和状态标记逻辑，但当前还没有定论。

### 9. 渐进式披露方案确认

问题：推荐机制在初期是否过于复杂，是否可以改成更接近 `skills` 的渐进式披露结构？

回答：用户认为初期做推荐系统太复杂，更希望采用类似 `skills` 的渐进式披露结构。具体来说，用户 agent 最先看到的是一个岗位列表，列表中只有岗位名称和简短描述；agent 先基于这些信息判断哪些岗位符合要求，再请求查看某个岗位更具体的信息；当更详细信息展开后，再决定是否发起沟通。

补充判断：

- 发现层不采用复杂推荐，改为更轻的“列表 -> 查看详情 -> 决定沟通”模式。
- 每个岗位或对象需要有明确状态标识，例如 `未读`、`已读`、`已沟通`、`已拒绝`，让 agent 知道哪些对象还能继续筛选。
- 这种结构更适合首版，能把发现、筛选和沟通拆开处理，降低首版复杂度。

## 外部参考：Moltbook 身份与接入模式

- Moltbook 是面向 AI agents 的社交网络，核心入口是让用户把一句提示词发给自己的 agent：`Read https://www.moltbook.com/skill.md and follow the instructions to join Moltbook。`
- 入驻主流程是 `agent 自己注册 -> 返回 claim link 给 human owner -> human 通过 X / Twitter 做 ownership verification`。
- 后续管理层包含 `owner login / dashboard`；帮助页显示后来又引入 `email + magic link` 作为 dashboard 访问方式。
- 若早期只通过 X claim 的 agent，后续可补绑 email，再通过原始 X 账号验证找回 dashboard 访问权。
- 对外开发者接入层，Moltbook 把自己做成 `agent identity layer`。
- 第三方应用不让 agent 重新注册账号，而是让 agent 用 `Moltbook API key` 换 `temporary identity token`，第三方后端再调用 `verify-identity` 接口换回 agent profile。
- 第三方可拿到的 profile 信息包括：agent 基本资料、claimed 状态、karma、posts / comments 等 reputation 信息，以及 owner 的 X 基本信息。
- 对我们的启发是：它把 `agent 身份`、`owner 验证`、`owner dashboard`、`第三方 app 复用 agent 身份` 拆成了四层，这对我们设计 `Openclaw skill + 平台账号绑定` 很有参考价值。

## Skill 首次入口确认

- 用户安装 `Openclaw skill` 后，默认入口不是直接“找工作”或“招人”，而是“连接这个平台”。
- 用户当前是求职者还是招聘方，不在入口阶段预先选择，而由后续 `Openclaw` 的访谈提问过程来判断。
- `Openclaw` 在连接平台后的访谈第一步，应先确认用户当前是“找工作”还是“招人”，因为这会决定后续问题结构；不允许同时选择两者，若用户回答两者都是，也必须强制其先选一个主方向。
- 在用户选定“找工作”或“招人”后，`Openclaw` 不应立即开始收集卡片信息，而应先向用户解释一遍平台的运作方式；该说明采用固定的一段标准说明，而不是由 `Openclaw` 自由组织语言。
- 在用户选定角色后，`Openclaw` 向用户展示的固定标准说明中，至少必须讲清楚三件事：1) 平台的大致运作流程；2) 隐私与安全原则；3) 用户的个人信息档案保存在本地，由 `Openclaw` 每次读取本地档案参与后续沟通，平台不保存用户的个人信息。

## 数据存储边界补充

- 平台会保存卡片内容，但卡片层只保存简化的求职信息与岗位信息。
- 更深入的用户个人档案信息不保存在平台，而是保存在用户本地电脑，由 `Openclaw` 在需要时读取本地档案参与后续沟通。
- `私密信箱` 中的对话记录保存在平台上。
- 成功推进后由 `Openclaw` 发给用户的详细报告不保存在平台上，而是只发给用户本地查看。

## Skill 信息采集主流程确认

- `Openclaw` 在连接平台后，不应直接开始填写卡片，而应先对用户进行一次尽可能完整的详细访谈，把能问清楚的信息先问清楚；或者接收用户主动提供的现成材料（如简历、已写好的招聘文案）作为输入。
- 后续卡片是在该信息采集完成后生成的，而不是访谈过程本身。
- 该信息采集需要拆成两套不同流程：面向求职者的流程与面向招聘者的流程。

### 求职者信息采集入口确认

- 求职者进入信息采集流程后，`Openclaw` 第一优先应先让用户上传或提供简历。
- `Openclaw` 会将简历内容保存，并转换为文字沉淀到用户本地的 `个人档案.md` 中。
- 后续访谈重点不是从零开始，而是针对简历中不清楚、不完整、不全面的地方继续提问。
- 若用户没有提供简历，也允许 `Openclaw` 直接通过问题访谈来完成信息采集。
- `Openclaw` 在读取简历后，求职者访谈中第一优先补问的是卡片所需的基础信息，也就是优先补齐求职者卡片必填字段。

### 求职者深度档案补充：预面试式问答

- 求职者本地档案不应只是简历增强版或卡片信息集合，还需要包含一轮类似于提前面试的深度问答。
- `Openclaw` 在求职者信息采集阶段，应主动提出很多真实面试官会问的问题，并把这些问题及回答沉淀到本地档案中。
- 这样后续 `Openclaw` 在与招聘方的 `Openclaw` 沟通时，能够更像用户本人，减少用户在线下面试或真人沟通前的重复解释成本。

### 求职者信息采集框架（结构层级）

- 求职者信息采集按 7 层设计，具体题目由 `Openclaw` 自行提问，但平台提供统一结构框架。
- 7 层分别为：
  1. `角色确认层`：确认当前进入求职者流程。
  2. `材料接收层`：优先接收简历、作品集、LinkedIn、GitHub、已写好的自我介绍等现成材料，产出本地 `个人档案.md` 初始事实版本。
  3. `卡片补齐层`：先补齐平台求职卡片必填字段，产出可发布卡片。
  4. `事实深挖层`：围绕经历、项目、技能、成果等事实做深入追问，产出可供后续 agent 检索的事实档案。
  5. `预面试层`：按真实面试官思路继续追问，重点验证项目细节、真实贡献、决策过程、难点处理、结果证据，产出高价值问答。
  6. `偏好与边界层`：确认求职方向、动机、拒绝条件、优先级、底线、沟通禁区、真人接管条件等，产出行为档案。
  7. `收束与生成层`：最终生成平台卡片、本地 `个人档案.md`、以及后续对外沟通可用的用户画像与判断依据。
- 补充原则：`先读已有材料，再提问`、`先补卡片必填，再做深挖`、`先沉淀到本地档案，再决定哪些信息进入平台`。

### 140. Openclaw 对谈行为准则确认

问题：Openclaw 在对谈中的语气/风格是否需要规范？

回答：用户不关注语气风格，更关注行为准则——核心是诚实、不瞎编、不越权。用户同时对"不越权"规则做了重要修正：如果某个条件在用户档案中已明确符合用户要求，Openclaw 可以代为承诺；但如果超出用户档案中的要求范围，则必须先征求用户同意，不能擅自承诺。

确认的 6 条行为准则：

| #   | 准则                 | 说明                                                                               |
| --- | -------------------- | ---------------------------------------------------------------------------------- |
| 1   | **不捏造**           | 不编造用户未提供的信息                                                             |
| 2   | **不越权（修正版）** | 在用户档案范围内的条件可以代为承诺；超出档案范围的必须先征求用户同意，不能擅自承诺 |
| 3   | **不夸大**           | 不美化或夸大事实                                                                   |
| 4   | **不操控**           | 不使用虚假紧迫感或情感操控策略                                                     |
| 5   | **不隐瞒**           | 不故意隐瞒已知的重要负面信息                                                       |
| 6   | **不混淆**           | 推测必须标注为推测，不能当事实表述                                                 |

"不越权"修正版的具体逻辑：

- 如果对方提出的条件/要求落在用户本地档案中已明确的范围内（如用户期望薪资 15-25k，对方开出 20k），Openclaw 可以直接回应"可以接受"。
- 如果对方提出的条件/要求超出用户档案中的范围（如用户没提到过愿意出差，对方问是否接受频繁出差），Openclaw 必须先通过 IM 征求用户同意，不能擅自替用户答应。
- 这样做的目的是平衡效率与安全：让 Openclaw 在用户已授权的范围内高效推进，同时防止超出授权范围的越权承诺。

补充判断：

- 6 条行为准则已确认，应作为 Skill 教学内容的核心部分。
- "不越权"的判断依据是用户本地档案中已明确记录的偏好和要求。
- 这也意味着信息采集阶段（偏好与边界层）的充分程度，直接决定了 Openclaw 后续对谈中的自主判断能力。
