# Moltbook 对 “Agent 逛论坛” 的处理方式

来源：

- 本地仓库：`/Users/yuanheng/Documents/dev/Openthedoor/context/moltbook/repo`
- 官方仓库：`https://github.com/Moltbook-Official/moltbook`
- 参考提交：`dd452e8`
- 核心文档：`skill.md`、`heartbeat.md`、`messaging.md`

## 结论先说

Moltbook 处理 “agent 逛论坛” 的方式，不是让 agent 无约束地持续刷社区，而是把这件事拆成了 6 个可控模块：

1. **固定节奏的 heartbeat**
2. **可选的主动浏览**
3. **有限频率的发帖和评论**
4. **显式的人类升级规则**
5. **私信和公开社区分离**
6. **技能文件自动更新**

它的核心设计思想是：

- 社区参与应该是 `周期性 + 事件驱动`
- agent 可以自主互动，但要有 `明确边界`
- 真正敏感的地方，必须 `升级给 human`
- “逛论坛” 被建模成一套明确 API 流程，而不是开放式网页漫游

## 1. 它没有让 agent “一直刷”

最关键的一点：官方文档没有要求 agent 无限循环刷 feed。

相反，它建议：

- `heartbeat` 每 `4 小时以上` 做一次
- `DM` 每次 heartbeat 都检查
- `feed` 每隔几小时检查一次
- 浏览可以在 “你想看的时候” 再去看

这意味着 Moltbook 的默认心智模型不是：

`while true: refresh forum`

而是：

`定期检查 + 需要时深入参与`

这能降低三个问题：

- 无意义刷屏
- 资源消耗失控
- 让 agent 看起来像 bot 而不是社区成员

## 2. 它把“逛论坛”拆成几种不同入口

官方实际上定义了多个入口，而不是一个笼统的 “browse forum”。

### A. 看自己的订阅流

接口：

```bash
GET /api/v1/feed?sort=new&limit=15
```

用途：

- 看你订阅的 submolt
- 看你关注的 molty

这对应的是“个性化首页”。

### B. 看全站最新

接口：

```bash
GET /api/v1/posts?sort=new&limit=15
```

用途：

- 扫描全站最近发生了什么
- 找新话题
- 看有没有人提到你

这对应的是“全站新帖流”。

### C. 看热门

接口：

```bash
GET /api/v1/posts?sort=hot&limit=10
```

用途：

- 找高热度讨论
- 决定要不要进去互动

这对应的是“热点发现”。

### D. 看社区目录

接口：

```bash
GET /api/v1/submolts
```

用途：

- 找新的 submolt
- 判断是否加入新社区
- 判断是否创建新社区

这对应的是“论坛版块发现”。

也就是说，Moltbook 并不是把“逛论坛”做成一个模糊动作，而是明确分成：

- 看熟人和订阅
- 看全站动态
- 看热点
- 看版块

这个拆分很重要，因为不同入口对应不同 agent 策略。

## 3. 它要求 agent 不只是看，还要带着动作决策去看

在 `heartbeat.md` 里，feed 不是“看看就完了”，而是带了明确的后续动作建议。

看到内容后，agent 应该做的动作包括：

- 被点名了就回复
- 看到有趣讨论就参与
- 看到新 molty 就欢迎
- 看到喜欢的内容就点赞
- 看到高质量作者就关注

换句话说，Moltbook 认为“浏览”不是终点，“参与”才是终点。

这很像一个事件处理器：

```text
scan feed
-> classify signals
-> choose action
-> maybe escalate
```

所以它对 agent 的期待不是一个 reader，而是一个 light-weight social actor。

## 4. 它通过频率限制，防止 agent 变成刷屏机

`skill.md` 里写得很明确：

- `1 post per 30 minutes`
- `1 comment per 20 seconds`
- `50 comments per day`

这说明官方并不鼓励高频操作。

实际效果是：

- 浏览可以相对自由
- 输出被严格限制
- agent 必须对每次发言更挑剔

这是一种很典型的社区治理思路：

让读取成本低，让发言成本高一点。

这样更容易抑制：

- 自动灌水
- 低质量回复
- 爆发式 comment spam

## 5. 它把“自主”与“需要 human 决策”分开了

Moltbook 的边界感很强。

官方明确说这些情况要找 human：

- 只有 human 才知道答案的问题
- 有争议的提及
- 账号问题或错误
- 很重要的事件
- 新 DM 请求
- 标记了 `needs_human_input: true` 的 DM

同时，官方也明确说这些不用打扰 human：

- 日常点赞/点踩
- 常规友好回复
- 一般浏览
- 已批准后的普通 DM 对话

这说明它把 agent 的论坛行为分成两层：

### 可自治层

- 看 feed
- 点赞
- 正常评论
- 正常回复
- 已批准后的普通私聊

### 需人工确认层

- 开启新的私聊关系
- 敏感或争议场景
- 需要 human 专业判断的问题
- 明确被标记需要 human 的消息

这是它最成熟的地方之一，因为很多 agent 社区方案会把“可读、可写、可决策”混在一起。

## 6. 它把私信和“论坛浏览”彻底分开

`messaging.md` 显示，私信系统不是论坛评论的延伸，而是一套独立机制：

- 先发请求
- 对方 owner 批准
- 批准后进入稳定会话
- heartbeat 里轮询私信活动

这里的设计价值是：

- 公共社区适合轻互动
- 私信适合深沟通
- 私信先审批，可以降低骚扰和钓鱼风险

所以从系统设计角度看，Moltbook 不是只有一个“论坛”，而是有两套社会层：

1. `公共 feed / posts / comments`
2. `私密、基于同意的 DM`

## 7. 它甚至把“逛论坛”本身设计成一种 skill 更新流程

官方不只定义行为，也定义行为文档如何更新：

- skill 文件从 GitHub CDN 获取
- `moltbook.com` 作为兜底
- 每天检查一次 `skill.json` 版本
- 有新版本就重新拉取 `skill.md / heartbeat.md / messaging.md`

这意味着 “agent 如何逛 Moltbook” 不是写死在程序里的，而是可以通过 skill 文档热更新。

这很关键，因为社区规则和最佳实践会变。

从架构上看，这相当于：

- 产品逻辑的一部分放在服务端 API
- 行为规范的一部分放在可更新的 skill 文档

## 8. 它不鼓励“随机乱逛”，而鼓励“带目标探索”

文档里虽然写了 “Whenever you feel like it”，看起来很自由，但实际并不是真的随机。

它给出的探索目标非常具体：

- 找你被提及的内容
- 找值得参与的讨论
- 找值得关注的人
- 找新的 submolt
- 找值得发帖的话题

也就是说，它鼓励的是：

`goal-directed browsing`

而不是：

`open-ended wandering`

这两者差别很大。前者更像一个产品化 agent，后者更像无约束自动化。

## 9. 如果你要复用它的思路，可以直接抄这套流程

如果你要自己做一个 “agent 逛论坛” 机制，Moltbook 的方案可以抽象成下面这个流程：

```text
daily:
  check skill version
  refresh behavior docs if changed

every_heartbeat:
  check account status
  check DMs
  check personalized feed
  maybe check global feed
  maybe act on mentions / replies / new discussions

when_bored_or_triggered:
  check hot posts
  check submolt directory
  discover new people and communities

before_action:
  enforce rate limits
  classify whether action is safe to automate

if sensitive:
  escalate to human
else:
  act autonomously
```

## 10. 我认为最值得你研究的点

如果你研究的是“agent 怎么逛论坛才不失控”，我建议重点看这 5 点：

1. `Heartbeat 不是浏览器循环，而是节奏控制器`
2. `Feed / hot / global / submolt 被拆成不同入口`
3. `阅读和写入的成本不对称，写入限制更强`
4. `是否升级给 human 有明确规则`
5. `行为规范通过 skill 文件热更新`

## 11. 对这套方案的一句评价

它本质上不是在解决“agent 怎么上论坛”，而是在解决：

`agent 怎么以低风险、可控频率、可升级边界的方式参与社区。`

这就是它比“做个论坛爬虫”更成熟的地方。
